## Rate snap (per plan)

The Simulink fixed-step discrete solver requires every sample time to be an
integer multiple of the base step. Base = **1 ms (1 kHz)**. The snapped rates:

| Rate | Native | Snapped | dt | Where it's applied |
|---|---|---|---|---|
| IMU LSM    | 833 Hz | 1000 Hz | 1 ms  | `IMU.Rate_Hz` overridden in base WS |
| IMU ADXL   | 800 Hz | 1000 Hz | 1 ms  | `ADXL.RatePostLaunch_Hz` overridden in base WS |
| EKF predict| 416 Hz |  500 Hz | 2 ms  | `Estimator.Dt` overridden in base WS |
| Baro       | 100 Hz |  100 Hz | 10 ms | native, no snap |
| Mag        | 100 Hz |  100 Hz | 10 ms | native, no snap |
| GPS        |  10 Hz |   10 Hz | 100 ms| native, no snap |
| Attitude   | 833 Hz | 1000 Hz | 1 ms  | matches IMU rate |
| Solver base| —      | 1000 Hz | 1 ms  | top-level `FixedStep = 1e-3` |

The override happens inside `build_casper_sim_phase0.m → snap_rates_for_visual_model_()`
**before** the library blocks load, so the embedded `1/IMU.Rate_Hz` etc.
expressions in the Rate Transition blocks evaluate to snapped periods at
compile time.

The snap is acceptable because this `.slx` is for **visual auditability** of
the data flow, not for byte-exact regression. The canonical byte-exact
reference remains `casper_phase0_run.m` at its native 1e-4 s solver and
exact 833/800/416 Hz sensor rates.

## Four semantic constraints

| # | Constraint | Visual implementation |
|---|---|---|
| 1 | Mag suppression until attitude init | Inside ATTITUDE subsystem: Unit Delay (Z⁻¹, initial=false) on init_complete feeds a boolean AND with mag_data_ready (from MAG outport 4). The AND's output drives the attitude_tick's `mag_new_eff` input. The unit delay is what breaks the algebraic loop (init_complete is both produced and would otherwise be consumed in the same step). |
| 2 | EKF init gated on attitude init | Inside ESKF subsystem: `init_complete` is an inport. The `eskf_step` MATLAB Function (via `eskf_step_helper`) holds the zeroed initial state and returns it whenever `init_done == false`. On the first call with `init_done && baro_new`, it re-seeds the ESKF state via `casper_eskf_state('init', Est, baro_alt)`. Equivalent semantics to a Rising-Edge Detector + Initialize Function pattern, simpler diagram. (This is the documented fallback from the plan.) |
| 3 | 11 s pre-pad window | Handled outside the diagram, in `casper_sim_config` / truth source `truth_ts`. Visual model is agnostic; whatever `truth_ts` contains is what the From-Workspace blocks read. |
| 4 | Post-pad metric slicing | Handled offline inside `casper_metric_*.m`. No diagram change. |

## Construction notes / decisions

- **Truth source is inline**, not a link to `T01_truth_pipeline/casper_sim_lib.slx`.
  Why: T01's `truth_source` block emits `TruthBus`; the rest of the diagram
  consumes `SensorInputBus`. Although the two buses have identical fields,
  Simulink treats them as distinct types and would need a non-trivial
  Bus → Vector → Bus converter in between. Inlining the 10 From-Workspace
  blocks + Bus Creator with `OutDataTypeStr='Bus: SensorInputBus'` is
  the same pattern every existing sensor visual-block test uses
  (`test_imu_block_visual_compile`, etc.), and avoids the type mismatch.
  T01's `.slx` is **not modified**.
- **Frame switches are inline MATLAB Function blocks**, not library links to
  `T07_frame_switch/frame_switch_block.slx`. Why: T07's `frame_switch`
  subsystem packages three switches (vec_NED, vec_std, q_std) into one box,
  with three inports the visual model would have to stub out. Simulink's
  type propagation can't reliably infer sizes for the stubbed inports —
  attempts with Ground blocks and shaped Constant blocks both errored on
  "errors in block body". The T07 logic itself is trivial
  (`vec_fw = [v(2); v(1); -v(3)]`) and gets inlined byte-identically to
  `casper_frame_switch_body.m`. T07's `.slx` is **not modified**.
- **ESKF and attitude use helper .m files**, not inline persistent state
  inside their MATLAB Function blocks. Why: Stateflow chart parser fails
  to statically infer the shape of struct-typed persistents whose
  shape depends on a `coder.extrinsic` call. Pushing the persistent
  state into a helper function (`eskf_step_helper.m` / `attitude_step_helper.m`)
  declared entirely extrinsic gives the chart a clean preallocated-output
  signature it can compile.
- **Validation logger is inline**, not a link to T10's `validation_block.slx`.
  Why: T10 was built as a top-level model (not a library), so its
  `validation_block` block can't be referenced as a subsystem from another
  model. The 14-channel skeleton is small enough to reproduce inline; the
  To Workspace variable names match T10's convention exactly so any
  downstream metric function expecting `log_est_state_x`, `log_sensor_imu`,
  etc. resolves unchanged. T10's `.slx` is **not modified**.
- **TruthBus → log_truth_bus path**: Signal Conversion (Virtual bus) →
  Bus to Vector → To Workspace. To Workspace can't accept a non-virtual
  bus directly, and a non-virtual bus can't feed Bus to Vector directly
  either — needs the intermediate `Virtual bus` conversion first.

## Known limitations / future work

- The attitude subsystem's `mode_pad` input is hard-pinned `true`. A
  flight-mode latch ("once |a_fw| > 3g, mode_pad := false forever") is a
  trivial Memory + Switch upgrade; out of scope for this pad-only smoke
  pass.
- The EKF receives `mach = 0` and `zupt_trig` driven by truth |vel_NED|
  rather than estimator |vel|. Matches the firmware behavior in
  `casper_phase0_run.m` for Phase 0 (truth-velocity ZUPT trigger).
- ADXL FIFO latch (`alt > 5 m → fifo_active=true`) is wired into the
  ADXL visual block already (T03 round 2) but not validated end-to-end
  in this pad-only smoke.
- All sensor library blocks reflect rate snaps via the base-WS overrides;
  the per-block test scripts (`test_imu_block_visual_compile` etc.) still
  use the native rates when called in isolation, because they re-call
  `casper_sim_config` which re-initializes `IMU.Rate_Hz` from T02 source.
  The snap is therefore confined to the visual top-level build path.
